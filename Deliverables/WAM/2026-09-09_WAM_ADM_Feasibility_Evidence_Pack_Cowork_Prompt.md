## 4. Point 1: Use cases

Sean asked for use cases, not value propositions. The distinction matters and the pack should honor it. A value proposition is a claim made to a buyer. A use case is a specific actor performing a specific task with specific data, producing a specific outcome. Only the second can be tested for feasibility, which is why Sean asked in these terms.

**Derive the use cases from the value propositions rather than replacing them.** The seven propositions in the record are the starting material.

Customer-facing:
1. One place to see everything you own: hardware, software licenses, warranties and lifecycle status across the install base.
2. No more surprise expirations: proactive alerts on renewals, warranty and support expirations.
3. Faster, cleaner onboarding: asset and license data normalized and structured, cutting manual reconciliation the customer absorbs today.

Internal commercial:
4. Governed triggers, not manual digging: renewal, warranty and refresh signals pushed to Sales and Sales Ops from the data.
5. Install-base intelligence for account conversations: visibility into what a customer already owns.
6. Already producing pipeline, not just promised: the first sales-notification release, 60-day expiration alerts, live since July.

Added 2026-08-26 and absent from every prior value statement:
7. Complex builds stay visible and serviceable: WAM carries the configured multi-component systems Wesco assembles and serializes into the customer install base record.

**Write each use case in a fixed structure**, so the set can be compared and rated:

| Field | Content |
|---|---|
| ID | UC1, UC2, and so on |
| Name | Short, in business language |
| Actor | Who performs it. Customer, Sales representative, Sales Operations, Managed Services delivery, ADM operations, product management |
| Trigger | What starts it |
| Task | What the actor does |
| Data required | The specific fields and structures, not the domain |
| Outcome | What changes in the business when it works |
| Value type | Revenue, cost avoidance, risk reduction, customer retention, or enablement of another use case |
| Beneficiary | Customer, commercial, Managed Services, or internal operations |
| Source proposition | Which of the seven it derives from, or new |

**Add the use cases the propositions do not cover but the record shows are real.** At minimum consider: the ADM enrichment service delivered for Violet Moyer's Microsoft AV data-gathering requirement (see 4.1); Managed Services onboarding of a new customer install base; internal supply chain program support, which is where the revenue is actually earned today; and entitlement event handling as defined in section 8 of `WAM_Data_Architecture.md`. A use case set that omits the motion that earns the money will not survive the meeting.

**Flag any proposition that does not decompose into a testable use case.** That is a finding in itself, not a gap to paper over.

- The diagram carries the message; the page carries a headline and a few labels. Title names the page, headline says the thing.
- Where the same picture is shown at more than one point in time, node positions stay constant across frames so the reader sees the picture change rather than reading unrelated diagrams.
- Orthogonal routing throughout. One continuous shape per connection, never a chain of segments; freeform where an elbow connector cannot make the route.
- Label tokens sit on top of the line with a solid fill and do not break it.
- Verify every connector endpoint against its node rectangle programmatically before shipping. An arrowhead standoff of about 0.07 inches is correct; anything further is a floating line.
- Native absolutely positioned shapes, not auto-layout. Mermaid is for drafting relationships only.
- Start from a real on-brand deck, keep the master, use the `Blank-with-Title` layout.
- Render every page to PNG and look at it before shipping.
