Executive Operating System

Architecture Canvas

Overview of components, boundaries, flows and use cases, as used. Drafted 2026-09-02. Working view, for my own use and for deciding what to change next.

The knowledge base is the asset. The record is upkeep. Every crossing of the boundary is a human step.

1. Component and boundary view

What the parts are, where the access boundary sits, and what moves across it. This is the anchor; the two views that follow use the same vocabulary.

Read the vertical axis as the asset stack

Durable knowledge on top, the session in the middle, living state below. The session reads upward and writes downward. Only the upward path compounds.

Read the horizontal axis as the pipeline

What happened, to evidence, to judgment, to output, to where it lands, and back into what happens next. The loop closes outside the system, not inside it.

Read the dashed line as an access boundary

Nothing inside it reaches the working environment. Every line that crosses carries a person marker because a person is the only transport across it.

2. The operating loop

The same system over time. Four cadences run at once; each maintains one of the two assets. The continuous lane is the one carrying most of the value.

3. Four use cases, traced through the components

Between them these four touch every component in view one. Each is drawn in the same vocabulary, so a trace can be followed on the anchor.

1 · Studio

A request becomes a deliverable, and the deliverable improves the base.

The highest value per unit of effort in the system, and the reason the knowledge base is worth maintaining. Nothing in this path touches the evidence loop.

2 · Radar

Activity becomes evidence, evidence becomes a decision about where to engage.

The loop the system was originally designed around. It maintains the record and produces the briefing; it does not add to the knowledge base by itself.

3 · Disposal

The record is pushed at me, and comes down only when I answer.

The only path that reduces anything. It is short, it is entirely dependent on my answer, and it is the one mechanism with a demonstrated record of clearing items.

4 · Compounding

A correction to one document becomes a permanent improvement.

The flywheel. It is the second-order effect of trace 1 and the reason first-draft quality moves at all. If corrections are applied to the document only, this path is broken and quality plateaus.

4. What the structure says

Three readings that follow from the drawing itself, not from performance data. Throughput and register health are deliberately not in scope here.

The boundary is crossed seven times, always by me

That is simultaneously the integrity guarantee, since nothing reaches the working environment unsupervised, and the throughput limit of the whole system.

Maintenance and value sit in different places

The record has three inbound maintenance paths; the knowledge base has one. Value concentrates where maintenance does not, which is worth remembering when deciding where to spend a session.

One path compounds and it is easy to skip

The thick line is the only edge whose value accrues. It fires at session end, has no scheduled trigger, and leaves no artifact when it is missed.

5. Intent, assumptions, validation items, exclusions

Per the deliverable template in the Mermaid standard, section 25.

Intent

  • Show at one glance what the parts are, which of them hold durable value and which hold live state, how work enters and leaves, and where a person is required.
  • Drawn as used rather than as designed: the studio is the primary output and the briefing loop is secondary, per the 2026-08-19 use case review.

Assumptions

  • Tool-agnostic by choice. The extraction step, the working session and the render step are drawn as roles, not products, so the picture survives a change of tooling.
  • The seven boundary crossings are drawn as human-carried because that is currently true. It is a property of the present access arrangement, not a design principle.
  • Outputs are grouped into three kinds. Individual document types are not enumerated.
  • The anchor view is hand-positioned. An auto-layout version was tried first and re-ranked the graph into an unreadable order, the same failure recorded in the Navigator diagram brief. Views two and three are auto-laid-out, which is safe at their complexity.

Validation items

  • Whether the Impact Ledger belongs in the operating record or beside the knowledge base. It holds evidence rather than live state, and it is the only record component with no inbound path from me.
  • Whether the render step is an output component or a service the session uses.
  • Whether portable prompts are a distinct output or a subtype of deliverable.
  • Whether these are the right four traces. They cover every component, but coverage is not the same as importance.

Exclusions

  • Named tools, products and vendors.
  • File and folder names. This is an architecture view, not a file inventory.
  • Retired components. A manual capture inbox and a register dashboard were built and cut; drawing them would misrepresent the system as used.
  • Throughput, register health and failure modes. Deliberately outside a clean structural view.
  • Cadence and timing, which are the subject of the second view rather than the first.
